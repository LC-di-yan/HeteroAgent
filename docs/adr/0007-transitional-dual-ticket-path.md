# 0007. 工单双实现（内存 TicketStore 与 MCP 工具）的过渡安排

- 状态：已接受（临时）
- 日期：2026-11-06
- 相关：`agents/ticket_handler.py`、`tooling/server.py`，方案 T-P1-07 / T-P2-03

## 背景

T-P1-07 把工单动作接到 `create_agent` 的工具循环，工具实现来自 MCP 服务端；
而历史代码里还有一个进程内 `TicketStore` 用于文本解析路径。两者并存会造成工单分裂。

## 决策

- 工具路径（模型支持 bind_tools 时）为**主路径**，工单写入 MCP 服务端；
- 文本解析路径仅作为降级（模型不支持工具调用 / 工具异常），写入内存 `TicketStore`；
- 工单号查询始终走规则快路径，避免无谓的模型调用；
- 两条路径都会在响应中返回真实工单号，不会编造（G10）。

## 后果

- 正面：升级期间不破坏既有测试与降级能力。
- 负面：存在两套存储，跨路径查询不一致（工具建的工单在 TicketStore 里查不到）。
- 偿还计划：T-P2-03 把 `TicketStore` 换成数据库实现，并让 MCP 工具与 Agent 共用同一仓储层，
  随后删除内存实现。在此之前，生产部署应始终启用工具调用（默认开启）。

## 备选方案

- 立即统一：需要先有数据库与迁移（P2 范围），现在做会放大风险。
