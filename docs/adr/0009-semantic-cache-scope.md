# 0009. 语义缓存只服务非个性化问题

- 状态：已接受
- 日期：2026-11-06
- 相关：`memory/semantic_cache.py`，方案 T-P3-04

## 背景

客服场景里大量问题是重复的（"收益率多少""怎么退款"），每次走完整 RAG 链路既费 token 也费延迟。
但"缓存回答"在金融服务里天然敏感：如果回答里混入了用户自己的工单号、持仓信息，
跨用户复用就是数据泄露。

## 决策

- 缓存键 = 归一化问题 + 租户 + 知识库版本；
- **带用户事实（`ContextStore` 命中）的请求既不读缓存也不写缓存**；
- 相似度阈值默认 0.95（语义缓存只在"几乎同一个问题"时命中，宁可不中也不误中）；
- 默认关闭（`SEMANTIC_CACHE_ENABLED=false`），需要产品方明确同意后开启；
- 没有 embedding 能力时退化为"归一化精确匹配"，不生成伪向量（与 ADR-0003 同一条原则）；
- TTL 1 小时兜底：知识库版本用文档数近似，文档内容变更但数量不变时靠 TTL 失效。

## 后果

- 正面：重复问题省一次完整链路；命中率可在 `cache.stats()` 观察；误用面被"非个性化"约束挡住。
- 负面：`kb_version` 用文档数近似，粗粒度；进程内实现不跨副本（多副本需换 Redis 版本）。
- 重新评估条件：出现"缓存答案与最新政策不一致"的投诉，或需要跨副本共享缓存。

## 备选方案

- 无条件缓存：跨用户泄露风险不可接受。
- 只做精确匹配：命中率过低，价值有限（当前实现仍保留该降级路径）。
