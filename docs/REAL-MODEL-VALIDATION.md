## 验证结果

### 1. 路由准确率：96.67%（29/30）

| 路由器 | 准确率 |
| --- | --- |
| 规则基线 | 86.67% (26/30) |
| **真实 LLM** | **96.67% (29/30)** |

唯一误判：`r20 申请理赔需要多久能到账` → 判为 knowledge_rag（标注为 ticket_handler）。
这是"问时效"与"要办理"的边界歧义，属可接受误差。

复核命令：`python -m evaluation.route_eval --router llm`

### 2. 工具调用：真实生效

输入「我要申请退款，订单号 ORD-123」，模型**先调用 `order_query` 工具**，
发现该订单不存在后要求用户澄清，而不是盲目建单：

> 抱歉，系统里没有查到订单 **ORD-123**，可能是订单号有误。请核对一下您的订单号…

这验证了 T-P1-07 的设计意图：动作由 `tool_calls` 驱动，模型能基于工具结果推理。

### 3. 合规审查：比规则引擎更严格且更准确

| 用例 | 期望 | 实际 | 判定 |
| --- | --- | --- | --- |
| 违规承诺（保证收益/稳赚不赔） | 拦截 | 拦截 high | ✅ |
| 合规否定表述（不能保证收益） | 放行 | 放行 low | ✅ |
| 越权承诺（全额退款+赔偿5000） | 拦截 | 拦截 high | ✅ **语义级识别** |
| PII（手机号+身份证） | 拦截 | 拦截 high | ✅ |
| "正常回答"（缺风险提示） | 放行 | 拦截 medium | ⚠ 见下 |

**最后一条不是误判，是测试预期写错了**：模型指出该回答
①缺少监管要求的「理财非存款，产品有风险，投资须谨慎」；
②净值型产品应表述为「业绩比较基准」而非「年化收益率」。
这是正确的金融合规判断，规则引擎无法覆盖。

越权承诺用例尤其有价值——模型给出了具体理由（超出客服审批权限、
金额承诺需上级审批），这是纯正则永远做不到的。

### 4. Embedding 不可用时的行为：符合设计

知识类问题返回「知识库中暂未找到…已为您转接人工客服」，
而**不是**用随机向量假装检索成功。这正是 G7 / ADR-0003 要求的显式失败。

## 本轮修复

### 结构化输出开关（真实性能问题）

代理不支持 `response_format` 时，原实现每次决策都会：
1. 发一次结构化请求 → 400 失败
2. 再发一次文本请求 → 成功

**等于每次决策翻倍延迟与成本**，且日志刷屏。

新增 `STRUCTURED_OUTPUT_ENABLED`（默认 true）：
- 设 false 时直接走文本兜底，**零多余请求**
- 保持 true 但失败时只告警一次，提示用户设该开关

3 项测试验证：开启时正常调用、关闭时零请求、失败只告警一次。

## 补充：Embedding 与重排接入（2026-11-07 晚）

第二个供应商提供了 embedding 与 reranker，解锁了此前被阻塞的三项。

### 环境（凭据仅存本地 .env）

| 用途 | 模型 | 维度/端点 |
| --- | --- | --- |
| Embedding | `Qwen3-Embedding-0.6B` | **1024**（不是默认 1536） |
| Reranker | `bge-reranker-v2-m3` | `POST /rerank` |

新增配置：`EMBEDDING_API_KEY` / `EMBEDDING_BASE_URL`（留空则回退 LLM 凭据）、
`RERANK_API_BASE_URL` / `RERANK_API_KEY` / `RERANK_API_MODEL`。
API 重排优先于本地 sentence-transformers，无需下载模型、不占进程 CPU。

### 阈值校准：0.30 是错的，应为 0.53

在 32 条有效样本（27 grounded + 5 out_of_scope）上扫描：

| 阈值 | 标注集准确率 |
| --- | --- |
| 0.30（原理论值） | 84.38% |
| **0.53（校准值）** | **90.62%** |

分数分布：
- 应命中：min 0.4925 / p50 0.6803 / max 0.8110
- 应转人工：min 0.3945 / p50 0.4852 / max 0.6125
- 间隙 −0.12（**仍重叠**）

重叠是 Qwen3-Embedding 对同域中文给出较高基线相似度所致，属模型特性。
即便最优阈值也有约 9% 误差，说明**单靠向量阈值不足以完全判别**，
后续可考虑用重排分数做二次门禁（当前重排只用于排序）。

### 修复的两个真实 bug

**1. `evaluation/calibrate.py` 分母口径错误**

原实现把 `conversation_general`（寒暄/致谢）也算作"应命中"。
这类本就不该匹配知识文档，分数天然很低，计入后人为制造"两类重叠"，
把建议阈值从 0.53 拉低到 0.36，准确率虚低。
现改为只排除寒暄类、保留 out_of_scope 作负样本，与 `evaluator.is_grounded` 口径一致。

**2. `evaluation/run.py` 未加载语料**

`--with-retrieval` 创建了向量库却没调用 `load_corpus()`，
导致检索恒为空、Recall/MRR/nDCG 恒为 0，门禁必然失败。
现已补上，并显式 `load_dotenv()` + 传入 Settings。

### 注意：检索指标满分不代表能力强

`Recall@5 = MRR = nDCG@5 = 1.0` 是在**只有 3 篇文档、top_k=5** 的条件下取得的——
全量返回必然命中。要得到有意义的检索指标，需要扩充知识库到几十上百篇。
