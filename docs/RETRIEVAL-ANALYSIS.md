# 检索质量归因分析

> 配套机器生成报告：[RETRIEVAL-BENCHMARK.md](RETRIEVAL-BENCHMARK.md)
> 本文是人工解读，指出数字背后的真实原因与局限。

## 1. 这轮做了什么

此前知识库只有 **3 篇、共 190 字**，检索指标恒为满分——不是系统好，是题目太简单。
本轮把语料扩到 **120 篇、5.7 万字**（296 倍），评估集扩到 **263 条**，
才第一次得到有区分度的数字，并因此挖出一个隐藏很深的评分 bug。

| 项 | 此前 | 现在 |
| --- | --- | --- |
| 语料文档 | 3 | 120 |
| 语料字数 | 190 | 57,364 |
| 评估用例 | 38 | 263 |
| 其中 grounded | 27 | 240 |
| 难负例（超范围） | 5 | 15 |

语料全部标注为**合成演示数据**，产品与条款均为虚构，零合规违规词。

## 2. 最重要的发现：BM25 归一化架空了置信度门禁

### 现象

首轮基准跑完，阈值扫描给出一个荒谬结果：
超范围样本的分数中位数（0.726）**比正样本（0.665）还高**，最大值达到 1.0。

逐条诊断后发现：

| 查询 | 命中文档 | score | 通道 |
| --- | --- | --- | --- |
| 帮我写一段Python爬虫代码 | accounts/a02_企业开户材料.md | **1.0** | BM25-only |
| 比特币现在什么价 | accounts/a12_绑卡单笔限额.md | **1.0** | BM25-only |
| 你们公司CEO是谁 | products/p29_康悦百万医疗险.md | **1.0** | BM25-only |

完全无关的查询拿到了**最高置信度**。

### 根因

BM25 原始分无上界，需要归一化到 [0,1] 才能与向量余弦同量纲比较。
原实现用 **min-max**：批次内排第一的永远是 1.0，单条命中时 span=0 也直接记 1.0。

这是**相对**归一化，与文档实际有多相关无关。
中文 bigram 分词下，几乎任何查询都能偶然命中某个文档，
于是每个查询都能拿到一个 1.0 —— 阈值门禁形同虚设。

### 修复

改用**绝对**饱和映射 score = s / (s + k)，k=20：

| 原始 BM25 分 | 归一化后 |
| --- | --- |
| 5 | 0.200 |
| 9.18（弱匹配） | 0.315 |
| 13.87 | 0.410 |
| 32.67（强匹配） | 0.620 |
| 100 | 0.833 |

同样的原始分永远得到同样的归一化分，不受同批其他文档影响，且永远小于 1.0。

### 效果

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 最优阈值 | 0.3368 | 0.4390 |
| 标注集准确率 | 94.51% | **97.65%** |
| 真负例（正确拒绝超范围） | 1 / 15 | **10 / 15** |
| 假正例（错误接受） | 14 | **5** |
| 正样本 p50 | 0.6652 | 0.6219 |
| 负样本 p50 | 0.7264（倒挂） | **0.4276**（正确） |
| 负样本 max | 1.0 | 0.623 |

修复前的 94.51% 是**类别不平衡造成的假象**（240 正 / 15 负，全接受就有 94.1%），
混淆矩阵 TP=240 FN=0 FP=14 TN=1 说明它几乎不拒绝任何东西。
修复后 TN 从 1 升到 10，才是真正在判别。

**召回指标几乎不变**（Recall@5 85.83% → 86.25%），说明修复只影响置信度门禁，不伤检索。

## 3. 重排的收益与代价

| 指标 | 基线 | +重排 | 变化 |
| --- | --- | --- | --- |
| Recall@1 | 66.25% | **80.00%** | **+13.75pp** |
| Recall@3 | 80.83% | 90.42% | +9.59pp |
| Recall@5 | 86.25% | 92.92% | +6.67pp |
| MRR | 0.7524 | 0.8551 | +0.1027 |
| nDCG@5 | 0.7717 | 0.8739 | +0.1022 |

**结论：重排值得默认开启。** Recall@1 提升 13.75 个百分点是很实在的收益——
对客服场景意味着首位命中率从三分之二提到五分之四。

代价：p95 延迟 1070ms → 1819ms（+749ms）。p50 基本不变（733→724ms），
说明重排耗时被向量检索的波动掩盖，只在长尾显现。

注意 Recall@10 反而下降 1.66pp——这不是退化，是基准脚本把重排结果截断到 top-5，
第 6-10 位没有结果。真实系统里重排后只用 top-3，不受影响。

## 4. 分类差异与评估集自身的局限

| 分类 | 用例 | Recall@1 | Recall@5 |
| --- | --- | --- | --- |
| accounts | 80 | **81.25%** | 93.75% |
| service | 80 | 63.75% | 88.75% |
| products | 80 | **53.75%** | 76.25% |

products 明显最差。看失败样例就明白了：

| 查询 | 期望文档 | 实际 Top-1 |
| --- | --- | --- |
| 这个理财没到期急用钱能提前取出来吗 | p02_进取理财365天 | a36_身份证过期处理 |
| 这个基金赎回要扣多少手续费呀 | p13_稳鑫短债债券基金 | s09_手续费退还 |
| 到期之后钱几天能自动到账啊 | p09_鑫睿打新策略理财270天 | a36_身份证过期处理 |

**这些查询里的「这个理财」「这个基金」是指代词**，脱离对话上下文根本无法确定是哪款产品。
标注却要求命中某一篇特定产品文档——这是**评估集的缺陷，不是检索的缺陷**。

生成器按「每篇文档生成用户问法」的思路工作，模型自然会写出「这个产品……」，
因为它是看着那篇文档写的。但真实用户说「这个」时，指的是上文提到的产品。

accounts 类之所以高，是因为它的问法天然自带区分词（法人来不了现场、人脸识别过不去、银行卡绑不上），
而 products 类有 10 款理财产品共享封闭期、赎回、到期等词，仅靠指代词无法区分。

### 这意味着什么

1. **products 的 53.75% 低估了真实能力**：其中相当一部分是无效标注。
2. **真实系统需要对话上下文消解指代**：当前 RAG 只用最后一句检索，
   接入短期记忆做 query 改写（把「这个理财」替换成上文产品名）能显著改善。
   项目已有 `rewrite_query`，但它只看当前 query，没吃对话历史。
3. 后续改进评估集：生成时禁止指代词，或显式提供对话上下文。

## 5. 仍然重叠的 5 个假正例

修复后仍有 5/15 超范围查询被判为「知识库有答案」。看分布：
负样本 max=0.623，正样本 min=0.433，区间重叠。

原因是 Qwen3-Embedding-0.6B 对同域中文给出较高基线相似度——
「帮我算一下房贷月供」与存款/理财文档在向量空间里确实接近。
这是小尺寸 embedding 模型的固有特性，不是 bug。

可选的改进方向（未实施）：
- 用重排分数做二次门禁（重排对无关查询给分极低，实测 0.00005 量级）
- 换更大的 embedding 模型（Qwen3-Embedding-4B/8B）
- 让 LLM 判断检索到的文档能否回答该问题，代价是多一次调用

## 6. 复核方式

```bash
make kb-stats     # 语料规模
make kb-golden    # 重新生成评估集（需 LLM）
make kb-bench     # 重跑基准（含重排 A/B，需 embedding + reranker）
python -m evaluation.render_report --json var/bench.json
```

离线回归（无需任何凭据）：

```bash
python -m pytest tests/test_kb_loader.py tests/test_retrieval_bench.py tests/test_memory.py -q
```
