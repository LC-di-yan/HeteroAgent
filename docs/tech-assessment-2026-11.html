核心结论

这个项目是一份保存完好的 2024 年末至 2025 年初 Agent 工程范式样本。分层架构、Supervisor 编排、混合检索、两阶段合规、超时重试与熔断等设计判断在 2026 年依然成立；真正落后的是实现手段：框架停留在 0.x 并手工重造了 1.x 已内置的能力，模型接入停留在 Chat Completions 与自由文本 JSON，MCP 是自造的 JSON-RPC 且与现行规范不兼容，语义检索因伪向量而实质失效。

更需要注意的是：有 4 项属于「规范级不兼容」（升级不是优化，是合规对齐），另有 9 处实现缺陷会造成错误路由、绕过防护或审计失效，其业务风险高于单纯的版本落后。建议先修缺陷、再升框架与协议、最后补可观测与评估闭环。不建议把强合规客服场景改成完全自主的多 Agent——可预测性在这里比自治度更有价值。

01架构与编排层

整体采用「API → Supervisor StateGraph → 子 Agent → 强制合规 → 聚合」的固定 DAG。这个结构本身适合金融客服；落后的是实现方式，以及多处设计与代码脱节。

现状

02模型接入与上下文工程

这是代差最集中、迁移收益最直接的一层：同样的业务逻辑，换接口与结构化输出可同时提升可靠性、降低延迟与成本。

B1Chat Completions + gpt-4o 属于上一代接入方式规范级
现状
全局使用 ChatOpenAI（Chat Completions），.env.example 与代码默认模型均为 gpt-4o；无推理模型参数、无模型分级、无 fallback 供应商。
基准
OpenAI 官方建议新项目迁移到 Responses API：跨回合保留加密推理项、内置工具、缓存利用率更高；并明确 Chat Completions 不会获得新的 Agent 能力。GPT-4o 已于 2026-02-13 在 ChatGPT 端退役（API 仍可用但属旧代），当前旗舰为 GPT-5 世代。[4]
影响
无法使用 reasoning items、服务端托管工具与更好的前缀缓存；长会话里反复重传历史的成本显著高于新接口。模型代际也直接影响工具调用与指令遵循的可靠性。

03工具协议层：最硬的规范级不兼容

项目自称「遵循 Anthropic MCP 标准」，但实现是一个进程内的自造 JSON-RPC 分发器。它既不符合旧版规范，也与 2026-07-28 现行规范全面不兼容。

C1自造 JSON-RPC，缺失协议全部核心机制规范级
现状
handle_jsonrpc 仅支持 tools/list、tools/call、ping；无 initialize（旧版）、无 server/discover（新版）、无协议版本协商、无 capabilities、无 transport（stdio / Streamable HTTP）、无 OAuth 2.1 / CIMD、无 resources / prompts、无 ttlMs / cacheScope、无 Mcp-Method / Mcp-Name 头、无 OTel traceparent 传播。
基准
MCP 现行规范为 2026-07-28：无状态核心、移除 initialize 握手与会话 ID、强制 server/discover 声明版本与能力、列表结果可缓存、CIMD 取代 DCR、Tasks / MCP Apps / EMA 成为扩展、旧 HTTP+SSE 传输与 Roots / Sampling / Logging 进入弃用期。该版本明确移除了 ping，而项目与 README 仍把 ping 列为三大方法之一。[1]
影响
任何合规 MCP 客户端都无法发现或连接此服务；生态工具（Inspector、网关、身份体系、缓存层）全部不可用。这不是「版本旧」，而是「不是 MCP」。

04记忆与检索层

混合检索（BM25 + 向量 + RRF）的架构判断在 2026 年依然主流，问题集中在 embedding、分块、重排与「记忆」语义四处。

D1hash 随机伪向量使语义检索实质失效高
现状
Embedding API 探测失败后，用 sha256(text) 播种 np.random.randn(1536) 作为向量；因分数普遍偏低，RAG 置信度阈值被下调到 0.05，等于取消阈值。
影响
向量相似度与语义无关（近乎随机），Hybrid Search 实际只剩 BM25 逐字匹配在起作用；/api/evaluate 给出的 Recall@K / MRR 也失去评估意义。这是全项目最影响效果的一处。
建议
把真实 embedding 作为启动必需条件（失败即拒绝服务，而非静默降级），或使用本地多语 embedding；随后把阈值恢复到有区分度的量级并用 Golden Set 校准。
memory/long_term.py:60-88, 108-149 · agents/knowledge_rag.py:20-24, 266-285
D2FAISS 实现停留在原型级：暴力索引、无生命周期管理中
现状
IndexFlatIP 全量暴力检索；无元数据过滤、无删除/更新/去重；save() 在 API 层从未调用（重启丢索引）；索引加载失败时重建 index 但保留 _documents，两者可能错位；add_document 不去重，doc_id 由内容哈希生成却可重复插入。
基准
生产通常使用支持过滤、增量更新与持久化的向量库（pgvector / Qdrant / Milvus），并把索引与元数据置于同一事务边界。
判断
知识库规模小的时候影响有限，但「对话摘要无限写入」会让它快速膨胀——见 D3。

D3「三层记忆」只是存储介质分层，不是 Agent 记忆高

工作记忆 = 进程 dict，短期记忆 = Redis list，长期记忆 = FAISS 文档。没有用户画像 / 事实抽取 / 时间衰减 / 冲突消解 / 事实版本，也没有 user / agent / session / org 作用域隔离。反而每轮对话都把原始用户消息与客服回复截断后写进知识库。

D4分块与分词未做中文化处理，重排模型选型错配中
现状
分块按 512 字符硬切（注释写 512 tokens，中文实际远超）；BM25 分词用「逐字中文 + 英文串」正则，无中文分词器 / n-gram，且每次检索全量重算 IDF；CrossEncoder 使用英文 ms-marco-MiniLM-L-6-v2，同步 predict() 在 async 函数中阻塞事件循环，依赖未写入 requirements。
基准

一条反向证据，避免过度升级：2026 年多项研究（RAW-RAG 等）显示，在 LoCoMo / LongMemEval 上，「保留原始对话 + 强 reranker 的朴素检索」可以胜过复杂的图记忆与事实抽取流水线，且摄入成本相差数十倍；上下文预算紧张时重排收益显著，预算宽裕时收益趋近于零。[8] 因此本项目的正确动作是「先换真 embedding + 停止污染知识库 + 换中文重排器」，而不是立刻引入图记忆或 mem0 之类的复杂框架。这些结论来自二手来源，落地前建议用自己的数据集复核。

05可观测性与评估

08哪些没有落后，应当保留

客观评估需要区分「方向错」与「手段旧」。以下五项在 2026 年仍然是正确的设计判断，重写时不必推倒。

K1FastAPI + Pydantic v2 + lifespan 异步基座保留
仍是 Python Agent 服务的主流组合，无需更换框架。
K2强合规场景用固定 Supervisor 图保留
可预测、可审计、可强制插入审查节点；比完全自主的多 Agent 更适合金融客服。建议保留拓扑，只替换节点内部实现与持久化机制。
K3规则引擎先行 + LLM 深度审查的两阶段合规保留
延迟与覆盖面的取舍合理；对应到 1.x 可用 PIIMiddleware + guardrail 中间件表达，而非放弃分层。
K4BM25 + 向量 + RRF 混合检索保留
2026 年仍是主流检索结构；需要替换的是 embedding、中文分词、分块与重排器，不是融合策略本身。
K5超时 / 指数退避 / 熔断 / 评估 / 追踪的意识保留
这些工程直觉领先于很多同期原型；只是应当从手搓迁移到框架中间件、官方 SDK 与标准遥测约定上。
