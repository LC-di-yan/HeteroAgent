# 面试项目业务描述话术

## 1. 一句话定位（30 秒电梯演讲）

> "这是一个基于 LangGraph 的 **Supervisor 编排多 Agent 智能客服系统**，面向金融场景，把客服能力拆成**意图路由、知识库问答、工单处理、合规审查**四个专业 Agent，用状态图编排成一个完整链路。核心特点是**所有回复强制经过合规审查**，这是金融客服的硬性要求。"

---

## 2. 业务背景与痛点（为什么做）

面试官想听"你发现了什么问题、为什么这个方案合理"：

| 痛点 | 说明 |
|------|------|
| 客服业务复杂度高 | 产品咨询、退款办理、理赔投诉、合规审查是**完全不同的专业领域**，需要不同知识库和判断标准 |
| 单 Agent 塞不下 | 把所有 Prompt 和工具塞进一个上下文窗口，Token 消耗大、意图互相干扰 |
| 金融合规是底线 | 客服一句"保证收益"就可能触发监管处罚，**所有回复必须审查**，这天然需要一个中央节点 |
| 知识更新频繁 | 产品政策经常变，用 RAG 改文档即可更新，不需要重新训练模型 |

> **总结句**："这个场景天然适合多 Agent：任务要专业化分工，回复要统一审查，知识要快速更新。Supervisor 编排 + 子 Agent 分工 + 强制合规，正好对应这三点。"

---

## 3. 业务功能全景（四大能力）

### ① 知识问答（KnowledgeRAG）
- 用户问产品收益、开户流程、退款政策 → 从向量知识库检索 → 生成回答
- 回答**标注来源**（product_faq.md），金融场景自动附风险提示
- 检索置信度低时**自动转人工**，不硬答（防幻觉）

### ② 业务办理（TicketHandler）
- 退款申请、开户办理、理赔、投诉 → 自动创建工单
- 识别**工单类型**（refund/claim/account_open/complaint）和**优先级**（资金安全=urgent）
- 工单号 `TK-20260819-XXXXXX`，支持创建→查询闭环

### ③ 合规保障（ComplianceChecker）
- **两阶段审查**：规则引擎毫秒级（正则 PII + 关键词）→ LLM 深度审查（越权承诺/误导）
- PII 自动脱敏（保留首尾3位）、风险等级 low→critical
- 检测到 Prompt 注入 / 高风险内容 → **自动进入人工审批队列**（Human-in-the-Loop）
- **否定词感知**：回答"不能保证收益"不会被误判为违规（控制误判率）

### ④ 交互体验
- 多轮对话（三层记忆：工作/短期/长期）
- SSE 流式响应（实时展示每个 Agent 处理阶段）
- 前端明暗主题切换

---

## 4. 核心业务流程（讲一条完整链路）

**以"用户申请退款"为例：**

```
用户："我要申请退款，产品买了3天"
  ↓
① 意图路由（Supervisor）—— FAQ未命中 → 路由缓存未命中 → LLM判断 → ticket_handler
  ↓
② 工单Agent —— 提取信息：类型=refund，优先级=medium → 创建工单 TK-20260819-XXXXXX
  ↓
③ 合规审查（强制）—— 规则引擎检查工单内容 → LLM 深度审查 → 通过
  ↓
④ 汇总回复 —— "工单已创建成功，工单号 TK-..."

同时：对话写入短期记忆（Redis），摘要异步写入长期记忆（向量库）
```

> **讲解要点**："合规审查是**强制必经节点**——路由到任何 Agent 最终都会过 compliance_check。这在 if-else 架构里很难维护，用 LangGraph 加一条边就行。"

## 5. 关键设计决策（体现架构能力）

| 设计决策 | 为什么这么选 |
|---------|-------------|
| 多 Agent 而非单 Agent | 专业分工 + 上下文隔离 + 合规需要独立审查节点 |
| Supervisor 编排 | 所有回复必须过合规，需要中央协调者保证流程可控 |
| RAG 而非 Fine-tuning | 知识频繁更新、回答可引用溯源、合规可追溯 |
| FAISS 起步 | 开发零依赖毫秒级；预留 Milvus 工厂切换生产可升级 |
| 两阶段合规 | 规则引擎高召回（毫秒级）+ LLM 高精确（语义级）互补 |
| LangGraph 而非 CrewAI | 显式状态管理、条件分支/循环、Checkpoint 断点、生产级 |

## 6. 量化成果（面试加分项）

> 用真实数据说话，面试官最认这个：

| 指标 | 数值 | 说明 |
|------|------|------|
| 检索质量 | **Recall@5 = 1.0，MRR = 0.75** | Golden Set 实测，4 条用例全部命中 |
| 规则引擎延迟 | **~1ms** | 正则 PII + 关键词毫秒级拦截 |
| Token 优化 | FAQ 早退 + 路由缓存 + 4000 token 预算 | 高频问题跳过整条 Agent 链路 |
| 容错 | 10s 超时 + 指数退避重试 3 次 | 超时返回降级话术不挂死 |
| 可观测 | 11 类 Agent 调用全部自动上报 | 调用次数/耗时/错误率可视化 |

## 7. 面试追问应对速查

| 面试官追问 | 应对话术 |
|-----------|---------|
| 和简单 if-else 路由有什么区别？ | "if-else 只能做单选路由，Supervisor 能做**流程编排**：状态共享、条件分支、强制合规边、Checkpoint 断点恢复、每个节点自动生成追踪 Span。加'所有回复必须过合规'这个需求时，if-else 要在每个分支末尾都加审查逻辑，LangGraph 只要加一条边" |
| 用户问"保证收益"为什么不拦截？ | "拦截的是**回答承诺**，不是用户的提问。用户问'能保证收益吗'是合法咨询，我们路由到知识库回答'不保证收益+风险提示'。早期规则引擎把'不能保证收益'误判为违规，加了**否定词感知**后只拦截无否定前缀的承诺" |
| 工单存在内存里？ | "演示用内存版 TicketStore 方便零依赖跑通；生产会替换为数据库。Agent 层已经通过 MCP 工具协议对接，换存储不影响编排层" |
| Embedding 为什么用 hash？ | "当前接的讯飞 MaaS 端点不支持 embeddings API，启动探测失败后自动降级为 hash 向量保证可用；代码已接入 OpenAI text-embedding-3-small，换支持 embeddings 的端点即自动启用真实语义向量" |
| 怎么保证所有回复都过合规？ | "图上强制边：knowledge_rag → compliance_check、ticket_handler → compliance_check，是架构级保证，不是代码级约定，绕不过去" |
| 合规误判率怎么控制？ | "两阶段互补：规则引擎宁可多报不漏报（召回优先），LLM 二次审查提高精确率；否定词感知处理'不能保证收益'这类合规表述；高风险直接拦截转人工" |
| 系统瓶颈在哪？ | "LLM API 调用是绝对瓶颈（每请求 2-3 次），FAISS 检索 2ms、Redis 不是瓶颈。优化方向：路由缓存、FAQ 早退、模型分级（小模型路由+大模型生成）" |
| 怎么评估系统好坏？ | "建了 4 条 Golden Set 的自动评估：检索用 Recall@K/MRR，生成用 Faithfulness（LLM-as-Judge）。实测 Recall@5=1.0，说明检索层没问题；Faithfulness 0.625 还有提升空间，下一步优化生成 Prompt" |

## 8. 演示节奏建议（5 分钟版）

1. **30s** 一句话定位 + 系统架构图（Supervisor → 4 Agent → 合规）

3. **1min** 演示工单：申请退款 → 展示工单号（边说边讲链路）
4. **1min** 演示合规：发一条 Prompt 注入 → 展示拦截 + 审批队列
5. **1.5min** 展示指标：/api/evaluate 评估报告 + /api/metrics 调用统计
